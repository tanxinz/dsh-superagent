## 1. 使用方式与开发边界

先完成 M0，再按 M1→M2→M3→M4→M5 推进阶段集成；本清单中任务号用于稳定引用，**同阶段实施顺序以“前置任务”为准，不按数字机械顺排**。例如基础 Exit 依赖 M2-24 结清机制。可以提前编写不依赖底座运行的 Fixture/契约草稿，但未通过阶段门槛不能宣称后续集成完成。

每项任务包含开发内容、工程交付物、可观察验收结果、责任角色、前置依赖和源设计章节。任务可直接转换为 issue；建议补齐实际负责人、分支/PR、工作量、状态、测试结果和 evidenceRef。原型任务的 P0 表示安全/一致性/阶段硬前置，P1 表示同阶段必须交付的功能或运维能力，**P1 不表示可以从 17 模块验收中删去**。

- 首期主栈：TypeScript ESM + Node.js + Cordis；沿用上游 pnpm、tsc、tsdown、Vitest。版本由 M0 实测锁定。
- 首期工程：fork `dsh-superagent-prototype`，在 `src/extensions/mesh/` 按需增加文件；本清单的新增文件名为建议落点，非声称仓库已经存在。
- 领域写入只有原生 Engine/受控扩展命令；同一个 SQLite Store、原生持久 Effects 和 Outbox。网络/模型调用在事务外，`Store.atomic` 同步回调内不允许 Promise/await。
- 全程单实例、单租户、SANDBOX；允许隔离 Mock 输出和受限真实 Session，不启用真实财务、生产写、真实推送/合并或普通渠道外发。
- Source Fixture、Schema Fixture、Mock RPC/Channel 可以用于设计允许的最小能力，但必须走真实接线。Jev 在线成功、真实 Worker 和双 Session Team 不可用硬编码替代。
- 本清单没有把其他 Reviewed/Validated 文档或此前验证包视作本文件的实施证据；如以后纳入，须核对源版本与测试对象。

### 5.2 状态与字段命名处理

实现时以源设计 §6.4 为唯一状态机；TS、数据库 CHECK/枚举、领域命令、API 和测试一起维护。`BLOCKED_CONFLICT` 是原因，不是新状态；`TeamRun.BLOCKED/PAUSED` 不存在；`ActionResult.FAILED` 不是自动终结 ActionRun 的指令。`EXPIRED` Patch 不能复活，旧 FAILED Step 只能派生新版本。

### 5.3 必须分开的五个事务边界

| 事务 | 只在事务内完成什么 | 提交后才允许什么 | 任务 |
| --- | --- | --- | --- |
| 计划提交 | 原生合法变更 + Plan/Run/引用 + 每项新动作 Effect | 异步执行准备；REUSED 无新执行 | M2-05 |

| 可写许可签发 | 根额度扣一次 + 唯一 Attempt + ISSUED/指纹 | 把一次调用资格交受信网关 | M2-09 |

### 5.4 新 Worker 的实际启动协议

1. 受信 Engine 建立或核验原生 Ticket/Mandate 和未启动 Assignment，必要时建立只读 Attempt 关联；此时不得运行业务 Worker。
2. 已有 Session 先核验有效绑定；新 Session 尚无 ID 时，以受信 Assignment 身份执行 beginAuthorizedWork，同库CAS固定根时钟并提交。
3. 仅分配未运行的 Session 句柄，持久写入绑定；再次核验根时限、当前安全epoch、Assignment与角色范围，全部成功后才释放业务上下文读取和工具执行。
4. 任何一步崩溃或复核失败均不得绕过后续检查；已提交根起点保持原值。创建 Session 无法与实际运行分离时，必须在足够早的原生Hook阻断，不能事后补记录。

该协议区分创建身份、开始计时、释放实际工作；只读工作也须通过，只有可写调用才另走Attempt计费与一次性许可消费。

## 10. 每项任务的统一完成条件与证据格式

### 10.1 完成条件（DoD）

- 实现满足任务输入/输出与源章节，代码在锁定的原生 Bundle 内真实调用，新增 API 不绕过 Engine/受信身份边界。
- 类型检查、相关原生回归、当前模块正常/失败/重放用例通过；事务、权限、恢复与竞争相关任务必须提供对应负向/故障测试，不能只有 happy path。
- 本阶段用到的迁移、TS 字段、索引、状态/错误码与 API 一致；重复启动不破坏数据，更新能保留历史事实。
- 关键状态有可追溯身份、时间、版本、操作者与 evidenceRef；敏感凭据、完整令牌、非必要原文不进入可见日志。
- 有实际运行结果和明确的 Fixture/Mock/在线模式标签。只编译通过可记 WIRED，不可记 PROTOTYPE；NOT_RUN/SKIPPED 不计入通过率。
- 相关配置、关闭/恢复方式、指标和已知限制更新；任何不支持的安全关键分支明确拒绝，不默认放行。
- 阶段出口由未直接编写该变更的审核人或受控复审流程检查关键证据；这是后续执行建议，本轮没有运行多 Agent 或代码复审。

### 10.2 建议 issue 记录模板

```yaml
task_id: M2-10
title: 一次性许可消费与撤权竞争
owner: 待指定
status: TODO                 # TODO / IN_PROGRESS / BLOCKED / IN_REVIEW / DONE
capability_level: UNVERIFIED # 未验收；验收后 WIRED / PROTOTYPE / PRODUCTION_READY
mode: SANDBOX
source_document_version: 9
source_sections: ["6.2", "6.8", "11.1"]
depends_on: [M2-09, M0-12]
code_commit: null
pr_ref: null
test_result: NOT_RUN         # PASS / FAIL / BLOCKED / NOT_RUN
evidence_refs: []
known_limits: []
```

`UNVERIFIED` 是本清单未验收标记，不是对源设计交付等级的新扩展。任务状态、能力等级、测试状态分别保存；业务 ActionRun/Plan 状态不能复用这些项目管理枚举。

### 10.3 证据目录与记录

建议仓库文档保存 `docs/acceptance/M0.md` 至 `M5.md`，运行证据放在受控工件目录并由索引引用：`evidence/<runId>/manifest.json`、测试报告、脱敏日志、SQLite 校验摘要、输入 Fixture 哈希、Mock 前后状态、真实 SessionEvent/模型请求引用、UI 需要时的截图。证据保存于项目约定的受控位置，不必把敏感数据库整库提交 Git。

每次运行至少记录 runId、taskId、源码 Commit、依赖与配置哈希、migration 版本、开始/结束时间、命令与退出码、输入/输出证据哈希、预期/实际结果和实际模式。模型请求记录必须区分请求发生时间与证据观察时间。源文未来变更时按章节/任务映射做影响分析，相关证据失效后重新验证，不能继续沿用旧 PASS。

### 10.4 必选能力、条件能力与阶段结论

本节是项目验收记录约定，不新增ActionRun/Plan等业务状态。每个任务记录 must_have（必选）、conditional_capability（条件能力）、fallback（设计明确允许的降级）与 evidenceRef；不能仅用一个总复选框隐藏其中未完成的能力。

- 必选项未通过：任务保持 BLOCKED/IN_PROGRESS，阶段不得通过。真实Jev、受限真实Worker、双真实Team Session、原子提交、根预算/许可安全和本阶段启用路径的拒绝均属于必选能力，不得以降级免验。
- 条件能力不存在而设计允许降级：先记录锁版探测结果；验证必选最小路径和明确禁用的高级分支；任务可按约定降级交付关闭，但相应高级能力必须保持UNVERIFIED/BLOCKED，测试仍为NOT_RUN，不能记PASS。关闭原因必须含降级决定与证据，不能删除原要求。
- 阶段结论使用 PASS（本阶段要求全部按目标验证）、ACCEPTED_WITH_LIMITATIONS（仅设计允许的降级路径通过且限制已登记）或 NOT_ACCEPTED（必选能力未通过）。后一种不允许进入依赖其安全事实的实际执行。条件验收不等于PRODUCTION_READY。
- ContextPatch缺可信请求Hook时可验真实注入及未证实/过期行为，不能验模型消费；LazySynth仅模板时可验安全模板输出，不能验实际模型合成；Effects缺安全重激活时可验等待/人工处置和禁止重复写，不能验自动恢复。
- Fixture与Mock在设计指定模块中是正常最小实现方式，本身不自动降低结论；关键区别是是否满足该模块明确的最小行为。不得将“不具原生接线的硬编码返回”算作Fixture通过。

M5的17/17应同时报告“最小行为通过数”和“存在条件能力限制的模块列表”。存在必选缺口时不得称完整覆盖；存在允许降级时明确称“最小覆盖，含已列限制”，不能用100项DONE推导全部目标能力可用。

### 13.3 两种 Patch 多请求回归时序

R24-A：Patch 有效时，实际请求1包含它且及时取得可信证明，合法进入 CONSUMED；请求2也在有效期内包含它，证明晚到后追加明细，状态仍 CONSUMED。不允许为了复用测试脚本而构造 CONSUMED→EXPIRED。

R24-B：两个实际请求均在 Patch/Session 原授权有效期内发生，但可信证明当时均不可取得；投递保持 DELIVERED_UNVERIFIED 后到期为 EXPIRED。两条证明此后到达，分别追加不可变明细并汇总 HISTORICALLY_CONSUMED，状态保持 EXPIRED。请求本身若发生在有效期后，只能作为 REJECTED 证据，不能被追认为历史消费。

R24-A/R24-B 是原 R24 的测试子例，不新增业务状态，也不改变 R01—R25 的编号和原文。请求发生时间与观察时间必须分别输入测试，不能共用一个测试时钟字段。
